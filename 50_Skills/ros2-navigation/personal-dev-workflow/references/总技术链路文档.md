# 工作台 · 总技术链路文档（最终对齐版）

> 本文档记录工作台核心功能的详细实现方案，属于「总文档」，不常修改。  
> 框架文档只描述「目录放什么、流程怎么走」，技术细节全部放这里。  
> 实现时请严格遵循《工作台需求文档》与《工作台框架文档》中的约定。

## 1. 整体架构概览

工作台采用「本地优先 + 轻量 Web」架构：

- 前端：轻量 Web 页面（HTML/CSS/JS 或 Vue/React，第一阶段可先纯静态 + 少量 JS）
- 文件操作：本地文件系统（优先通过本地后端或浏览器 File System Access API）
- 启动：Bash 脚本一键拉起（`scripts/start.sh`）
- 数据存储：全部落在本地项目目录，无云端依赖（第一阶段）
- 项目骨架生成：使用 **Cookiecutter**（推荐）或 Copier 实现固定目录结构生成

核心数据流：
用户操作（Web） → 触发本地文件读写 / Cookiecutter 生成 → 实时反馈到页面

## 2. 启动链路（scripts/start.sh）

### 目标
一键启动工作台 Web 界面，尽量少步骤。

### 实现方案
1. `start.sh` 检查是否已有服务在运行（端口占用检测）
2. 如果没有，启动本地静态服务器（或简单 Node/Python 服务）托管 `web/` 或 `src/frontend/` 目录
3. 自动打开默认浏览器访问 `http://localhost:xxxx`
4. 支持可选参数：指定端口、指定背景图、静默启动等

推荐实现方式（二选一或都支持）：
- 纯静态：`python -m http.server` 或 `npx serve`
- 带后端：Node.js Express / Python FastAPI（方便后续文件操作与 Cookiecutter 调用）

## 3. 新建项目 & 目录生成链路（核心）

### 目标
用户输入主项目名后，自动生成完整固定目录结构。

### 实现方案（推荐使用 Cookiecutter）
1. Web 页面收集用户输入的主项目目录名
2. 调用 Cookiecutter（命令行或 Python 库）生成项目
3. 模板需严格对应框架文档定义的固定结构：

```
{用户自定义主项目名}/
├── docs/
│   ├── requirements/          # 总需求文档
│   ├── framework/             # 框架文档
│   └── tech-chain/            # 总技术链路文档
├── requirements/
│   ├── image_base/            # 截图
│   ├── single/                # 单次开发需求文档
│   └── archive/               # 历史版本 / 原始讨论稿
├── rules/
├── bugs/
│   └── image_base/
├── ideas/
├── scripts/
│   └── start.sh
├── src/ 或 web/
│   ├── frontend/
│   └── backend/               # 可选
├── assets/
│   └── backgrounds/
└── README.md
```

4. 生成完成后，在对应目录放入默认的「放置类型说明」文件（只读标记）
5. 页面弹出提醒：各目录应放置的文档类型

### Cookiecutter 模板要求
- `cookiecutter.json` 至少包含 `project_name` 变量
- 支持后置钩子（`hooks/post_gen_project.py`）做初始化（写默认说明文件、权限处理等）
- 主目录名由用户输入，其余目录名固定，不轻易变更

### 关键技术点
- 创建失败时给出明确错误（权限、已存在、Cookiecutter 未安装等）
- 支持「覆盖 / 跳过已存在目录」选项
- 第一阶段可先用命令行调用 Cookiecutter，后续再封装成 Web 接口

## 4. 文档拖放放置链路

### 目标
支持拖动文件，最终光标停留的位置即为目标放置位置。

### 实现方案
1. 页面提供可拖放区域（或整个工作区）
2. 监听 `dragover` / `drop` 事件
3. 获取当前鼠标/光标所在的目录节点
4. 将文件移动或复制到该目录
5. 支持多文件、文件夹拖入
6. 拖放完成后刷新目录树显示

技术选型建议：
- 现代浏览器 File System Access API（权限更强）
- 或传统 `<input type="file" webkitdirectory>` + 后端上传

## 5. 灵光一闪记录链路

### 目标
快速记录想法，用户可自定义文件名。

### 实现步骤
1. 页面提供输入框（标题/文件名）+ 内容编辑区
2. 用户确认后，将内容保存为 `ideas/{用户自定义文件名}.md`
3. 支持后续打开、编辑、删除
4. 可选：一键插入当前时间戳或标签

## 6. 背景自定义链路

### 目标
支持自定义背景图 + 默认背景板。

### 实现方案
1. `assets/backgrounds/` 存放默认图片和用户上传图片
2. 页面设置区域提供：
   - 上传自定义背景
   - 选择已有背景
   - 恢复默认
3. 使用 CSS `background-image` 实时切换
4. 用户选择后写入本地配置文件（或 localStorage + 文件同步），下次启动自动加载

## 7. 提醒与引导链路

### 目标
在关键节点自动提醒用户该做什么。

### 实现方式
- 新建项目完成后 → 弹出「初始需求文档必填项」提示（使用场景、解决的问题、接口定义、阶段性目标、最终目标）
- 准备进入编码阶段 → 弹出「是否先写最简 README」提示，并展示三阶段写法
- 日常可配置「规则文档更新提醒」
- 提醒内容做成可配置模板，方便后续扩展

## 8. 需求文档管理链路

### 目标
清晰区分「当前生效总需求」与「单次开发 / 历史版本」。

### 实现约定
- **正式总需求文档**：固定放在 `docs/requirements/工作台需求总文档.md`，平时只改这一份
- **单次开发需求**：放在 `requirements/single/{日期或功能名}_需求.md`
- **历史版本 / 原始讨论稿**：统一放入 `requirements/archive/`，命名示例：
  - `第一版讨论需求.md`
  - `第二版润色前.md`
  - `v1.0_需求冻结.md`
- 历史版本只读，不再修改；文件开头建议加历史说明标记

### 页面支持建议
- 新建单次需求时，默认引导保存到 `requirements/single/`
- 提供「归档当前需求到 archive」快捷操作

## 9. 修 Bug 文档链路

### 目标
每次修 Bug 时，规范记录「原因 + 手法 + 截图」。

### 推荐写法模板（放在 `bugs/` 下）

```markdown
# Bug 标题 / 简要描述

## 1. 报错原因
- 错误信息：
- 触发条件：
- 根本原因分析：

## 2. 修复手法
- 修改了哪些文件：
- 具体改动说明：
- 验证方式：

## 3. 截图
（把相关截图放在同目录的 `image_base/` 下，并在此处引用）
```

### 实现支持
- 页面提供「新建 Bug 记录」按钮
- 自动创建 `bugs/{日期或名称}_bug.md` + 对应 `image_base/` 文件夹
- 支持直接拖入截图到 `image_base/`

## 10. 与外部 AI 协作辅助链路（后续阶段）

当前阶段仅做引导，不强制对接本地/云端 AI：

1. 导出当前需求/框架/技术链路文档为 Markdown
2. 用户手动复制到外部 AI（Grok、智谱等）或本地 API 对话
3. 讨论完成后，把新版本文档拖回对应目录（`docs/` 或 `requirements/single/` / `archive/`）
4. 后续可扩展：一键复制、模板提示词、本地 API 调用

> 说明：用户当前采用「直接接本地 API 写代码」的方式，技术文档需保持完整、可直接复制给本地 AI 使用。

## 11. 技术实现优先级建议

**第一阶段（必须先做）**：
- `start.sh` 启动
- 基础 Web 页面 + 背景切换
- 灵光一闪记录
- 新建项目目录生成（使用 Cookiecutter 实现固定结构，含 `single/` 与 `archive/`）

**第二阶段**：
- 拖放放置
- 各目录放置类型只读/可编辑
- 提醒系统

**第三阶段**：
- Bug 记录完整模板支持
- 需求文档单次/归档管理体验优化
- 与本地/外部 AI 的辅助导出/导入体验优化

## 12. 关键实现约束（给本地 AI 的强制要求）

1. 目录名（`docs/`、`requirements/`、`rules/`、`bugs/`、`ideas/`、`scripts/` 等）为固定命名，不得随意更改。
2. 主项目目录名必须由用户输入，其余结构自动生成。
3. `bugs/` 下的文档必须包含「报错原因 + 修复手法 + 截图」。
4. 历史需求版本只放 `requirements/archive/`，正式总需求只放 `docs/requirements/`。
5. 启动必须通过 `scripts/start.sh`。
6. 第一阶段优先保证「能启动、能生成目录、能记录灵感、能换背景」，其余功能可后续迭代。
