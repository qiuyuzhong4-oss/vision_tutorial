# 二,C++语法的一些规范文件

# 	(一些变量名或者是文件名命名的时候注意大小写)

​	这里主要写 C++ 工程里面常见的规范文件或者配置文件。它们不是 C++ 语法本身,但是会影响代码怎么编译、依赖怎么声明、程序怎么启动、参数怎么读取。

​	在 ubuntu 和 ROS2 环境里面尤其要注意文件名大小写。Linux 对大小写敏感,所以 `CMakeLists.txt`、`Makefile`、`package.xml` 这类文件名不要随便改大小写。



## 1,CmakeList

​	这里准确的文件名一般是 `CMakeLists.txt`。它是 CMake 工程的核心配置文件,用来告诉编译系统这个工程叫什么、使用什么 C++ 标准、有哪些 `.cpp` 文件要参与编译、需要链接哪些库。

​	不要写成 `CmakeList`、`CmakeLists` 或者 `cmakelists.txt`,否则 CMake 可能找不到这个配置文件

​	在普通 C++ 或 OpenCV 工程里面,它主要负责把源文件编译成可执行程序。在 ROS2 的 C++ 包里面,它还会配合 `ament_cmake` 使用,负责声明节点程序、安装节点、安装 launch 文件、安装 config 文件、链接 ROS2 依赖库。

​	如果 CMakeLists 写错,常见结果是:源文件没有被编译、库没有链接上、头文件找不到、ROS2 节点编译出来了但是运行时找不到。



## 2.makfile

​	这里准确的文件名一般是 `Makefile`。它也是用来描述 C++ 工程怎么编译的文件,内容会直接告诉 `make` 命令应该调用哪个编译器、使用哪些编译参数、源文件有哪些、最后生成什么目标文件。

​	Makefile 的优点是直接,适合小工程或者理解 C++ 编译过程。缺点是项目一复杂就不太好维护,特别是依赖库多、源文件多、路径多的时候。

​	在 ROS2 里面一般不手写 Makefile。ROS2 的 C++ 包通常使用 `CMakeLists.txt` 加 `package.xml`,然后通过 `colcon build` 构建。所以 Makefile 可以了解,但在 ROS2 项目里面不是必须文件。



## 3,package.xml

​	`package.xml` 是 ROS2 包的说明文件,可以理解成一个 ROS2 package 的“身份证”。它会说明这个包叫什么名字、版本是多少、作者是谁、许可证是什么、依赖哪些 ROS2 包或第三方库。

​	在 ROS2 的 C++ 包里面,`package.xml` 通常和 `CMakeLists.txt` 同级放在包的根目录。`CMakeLists.txt` 负责怎么编译,`package.xml` 负责告诉 ROS2 这个包是什么、需要什么依赖。

​	如果 `package.xml` 里面缺少依赖声明,可能会导致别人编译你的包时找不到依赖,或者在工作空间里面构建顺序不正确。所以 ROS2 工程里面它是必须要认真写的文件。

​	还可以使用rosdep来进行批量配置环境,只要在package.xml里面配置好需要的包的版本,官网等信息就行



## 4,launch文件

​	launch 文件一般放在 `launch` 文件夹里面,常见后缀是 `.launch.py`。它的作用是统一启动一个或多个 ROS2 节点,也可以在启动时设置参数、设置命名空间、重映射话题名。

​	如果一个项目只运行单个节点,可以暂时不用 launch 文件。但只要项目里面有多个节点,或者每次启动都要带很多参数,就应该写 launch 文件。

​	launch 文件不是 C++ 语法文件,但是在 ROS2 工程里面非常常见,属于运行层面的规范文件。



## 5,config参数文件

​	config 文件一般放在 `config` 文件夹里面,常见格式是 `.yaml`。它的作用是把程序参数从代码里面拿出来,方便修改和复用。

​	比如相机参数、阈值参数、滤波参数、识别参数、机器人尺寸参数,都适合放到 config 文件里面。这样不用每次改参数都重新改 C++ 代码、重新编译。

​	在 ROS2 里面,config 文件经常配合 launch 文件一起使用。launch 文件负责启动节点,config 文件负责给节点传参数。



## 6,msg文件

​	`msg` 文件一般放在 `msg` 文件夹里面,用来定义 ROS2 里面自定义的话题消息类型。

​	如果已有的 `std_msgs`、`sensor_msgs`、`geometry_msgs` 等消息类型够用,就不需要自己写 msg 文件。如果你要发布自己的识别结果、装甲板信息、目标位姿等特殊数据结构,就可能需要自定义 msg。

​	自定义 msg 之后,C++ 节点就可以像使用普通类型一样使用这个消息类型,但是同时也要在 `CMakeLists.txt` 和 `package.xml` 里面声明相关生成和依赖关系。



## 7,srv文件

​	`srv` 文件一般放在 `srv` 文件夹里面,用来定义 ROS2 的服务通信格式。服务通信可以理解成“一问一答”,客户端发请求,服务端返回结果。

​	如果你的功能是持续发布数据,一般用 topic 和 msg。如果你的功能是需要请求一次、返回一次结果,比如触发标定、切换模式、查询状态,就可以考虑 srv。

​	srv 文件同样不是普通 C++ 文件,但是它会生成 C++ 可以使用的服务类型。



## 8,action文件

​	`action` 文件一般放在 `action` 文件夹里面,用来定义 ROS2 的动作通信格式。action 适合执行时间比较长、需要反馈进度、还可能被取消的任务。

​	比如导航到某个位置、机械臂执行一个动作、机器人完成一个较长任务,这种就比普通 srv 更适合用 action。

​	视觉入门阶段不一定马上用到 action,但是在完整机器人系统里面它是 ROS2 重要的接口规范文件之一。



## 9,urdf和xacro文件

​	`urdf` 和 `xacro` 文件主要用于描述机器人模型,包括连杆、关节、坐标系、碰撞体、视觉模型等。

​	如果只是写一个普通 C++ 视觉节点,不一定需要它们。如果要做机器人整体仿真、TF 坐标关系、RViz 模型显示、导航或机械臂相关内容,这些文件就很重要。

​	`xacro` 可以理解成更方便维护的 urdf 写法,最后通常会展开成 urdf 给 ROS2 使用。



## 10,rviz配置文件

​	`rviz` 配置文件一般放在 `rviz` 文件夹里面,用于保存 RViz2 的显示配置。

​	它记录了 RViz2 里面打开了哪些显示项,比如图像、点云、TF、Marker、机器人模型等。这样下次打开 RViz2 时不用重新手动配置界面。

​	这个文件不是必须的,但在调试视觉、雷达、导航、机器人模型时很方便。





# 三,C++必要的一些库或者说他的编译器

​	这一部分主要是把“写 C++ 会遇到的工具、库、编译器”分清楚。很多东西名字看起来都像配置,但作用并不一样。有的是负责编译代码的,有的是负责组织工程的,有的是负责安装依赖的,还有的是别人已经写好的库或者厂家提供的驱动。

​	可以先按下面这个顺序理解:

- 编译器:负责把 `.cpp` 变成机器能执行的程序
- 基础工具:负责提供编译 C++ 时常用的一组命令
- 构建工具:负责组织多个源文件、头文件和库怎么一起编译
- 依赖工具:负责检查或者安装工程需要的依赖
- C++ 库:负责提供别人已经写好的功能,让你不用从零开始写
- SDK:通常是厂家提供的开发包、驱动、接口或者示例程序



## 1,gcc/g++

​	`gcc` 和 `g++` 都是 GNU 编译器套件里面的工具。简单理解,`gcc` 主要常用于编译 C 程序,`g++` 主要用于编译 C++ 程序。

​	写 C++ 时更常见的是 `g++`。它负责把 `.cpp` 文件编译、链接,最后生成可以运行的可执行文件。如果没有编译器,C++ 源代码就只是文本,不能直接运行。

​	在 ubuntu 环境下,很多 C++ 工程底层最终都会调用 `g++`。即使平时用的是 CMake、Makefile 或 ROS2 的 `colcon build`,它们背后也会间接调用编译器。



## 2,build-essential

​	`build-essential` 不是一个单独的 C++ 库,而是 ubuntu 里面常用的一组基础编译工具集合。它通常包含 `gcc`、`g++`、`make` 等基础工具。

​	如果一台新的 ubuntu 电脑不能正常编译 C++ 程序,经常就是因为这些基础工具没有装全。对于刚开始配置 C++、OpenCV、ROS2 环境的人来说,它属于比较基础的开发环境组件。



## 3,cmake

​	`cmake` 不是编译器,它是构建配置工具。它主要读取 `CMakeLists.txt`,然后根据里面的内容生成真正的构建文件。

​	它的作用是告诉系统:这个工程有哪些源文件,要生成什么程序,要链接哪些库,头文件路径在哪里,用什么 C++ 标准。

​	在普通 C++、OpenCV、ROS2 C++ 工程里面都很常见。尤其是 ROS2 的 C++ 包,基本都是围绕 CMake 和 `ament_cmake` 来组织编译的。



## 4,make

​	`make` 是构建执行工具。它会读取 Makefile 或者 CMake 生成出来的构建规则,然后真正开始调用编译器去编译项目。

​	可以把 `cmake` 和 `make` 简单分开理解:cmake 更像是生成规则的人,make 更像是按照规则干活的人。

​	在 ROS2 里面通常不直接手写 Makefile,也不一定直接输入 make,因为 ROS2 常用 `colcon build` 统一构建整个工作空间。但 make 仍然是 C++ 编译体系里很基础的工具。



## 5,colcon

​	`colcon` 是 ROS2 常用的工作空间构建工具。普通 C++ 工程可能只编译一个文件夹,但 ROS2 工作空间里经常有很多 package,它们之间还有依赖关系。

​	`colcon` 的作用是扫描整个 ROS2 工作空间,找到里面的 package,然后按照依赖顺序构建它们。对于 ROS2 C++ 来说,它会配合 `package.xml` 和 `CMakeLists.txt` 使用。

​	所以在 ROS2 里面,可以把 `colcon` 理解成比 cmake/make 更上层的构建工具。它不是 C++ 语法,但写 ROS2 C++ 工程基本会遇到。



## 6,ament_cmake

​	`ament_cmake` 是 ROS2 里给 CMake 工程使用的构建系统。普通 CMake 只知道怎么编译普通 C++ 工程,而 ROS2 还需要处理 package、节点安装、消息生成、依赖导出等事情。

​	`ament_cmake` 就是把 CMake 和 ROS2 的 package 机制连接起来。写 ROS2 C++ 包时,`CMakeLists.txt` 里面经常会使用它提供的功能。

​	如果说 `CMakeLists.txt` 是你写的工程规则,那 `ament_cmake` 就是 ROS2 提供的一套规则和工具,让这些 C++ 工程能被 ROS2 正确识别、编译和安装。



## 7,rosdep

​	`rosdep` 不是编译器,也不是 C++ 库。它是 ROS 里面用于安装系统依赖的工具。

​	当一个 ROS2 包在 `package.xml` 里面写好了依赖,`rosdep` 可以根据这些依赖名字,帮你安装对应的 ubuntu 软件包。这样别人拿到你的工程时,不用一个一个猜缺什么库。

​	所以 `rosdep` 的重点不是编译,而是“把依赖环境补齐”。它和 `package.xml` 的关系比较紧密:package.xml 写清楚需要什么,rosdep 才知道该安装什么。



## 8,rclcpp

​	`rclcpp` 是 ROS2 的 C++ 客户端库。写 ROS2 C++ 节点时,发布话题、订阅话题、写服务、写参数、写定时器等功能,很多都要通过 `rclcpp` 来完成。

​	如果只是写普通 C++ 程序,不需要 `rclcpp`。但如果写的是 ROS2 C++ 节点,它基本就是最核心的库之一。

​	可以简单理解为:`rclcpp` 负责让 C++ 程序接入 ROS2 通信系统。



## 9,pkg-config

​	`pkg-config` 是用来查询第三方库编译参数和链接参数的工具。它本身不是 C++ 库,也不是编译器。

​	一些库安装好之后,会提供 pkg-config 信息。这样编译程序时,系统就能知道这个库的头文件在哪里、库文件在哪里、链接时应该加什么参数。

​	在一些 OpenCV 或手写 Makefile 的工程里面可能会看到它。使用 CMake 时不一定直接接触它,但理解它有助于明白“为什么有些库安装了还需要配置路径”。



## 10,C++标准库

​	C++ 标准库是 C++ 自带的一组基础库。比如字符串、数组、向量、输入输出、文件读写、智能指针、算法等,都属于标准库提供的能力。

​	它和 OpenCV、ROS2 这种第三方库不一样。标准库是写 C++ 几乎一定会用到的基础部分,不需要像第三方库那样单独配置复杂依赖。

​	比如写视觉或 ROS2 时,虽然主要可能在用 OpenCV 和 ROS2,但底层还是经常会用到标准库里的容器、字符串、时间、数学和文件处理能力。



## 11,SDK

​	SDK 可以理解成厂家提供的一整套开发包。日后写程序时,经常会使用厂家已经写好的驱动程序、接口函数、头文件、库文件、示例代码或者单独的软件工具,这些通常都可以算在 SDK 里面。

​	SDK 的存在形式不一定只有一种。有的 SDK 是系统里面单独运行的软件,有的 SDK 是给 C++ 程序调用的库,有的 SDK 是一组头文件加动态库或者静态库。比如相机、雷达、电机、采集卡这类硬件,厂家一般都会提供对应 SDK。

​	实际使用时,我们常常会把需要用到的驱动、头文件、库文件或者封装好的接口放到自己的代码工程里面统一管理。这样项目迁移或者给别人使用时更清楚。不过最好保留 SDK 的版本信息和说明,不要把厂家提供的内容改得完全看不出来来源。



# 四,学C++的时候会遇到的一些难点

## 1,特殊符号:

像是@,#,:,"这些混乱的符号而言我们平时使用的都是中文,相信应该没有那个语文是很强的,会来吃编程这碗饭,英语就更不用说了,就那样,在任何语言的编写中都是离不开特殊符号和英文的,英语有成千上百个单词,而我们的C++语言只有几十个特殊符号的用法,想必是会简单许多,接下来,就来介绍各种特殊符号以及他们单一时和组合是的用途:

(1)全部的特殊符号:① `#` ② `<` ③ `>` ④ `(` ⑤ `)` ⑥ `{` ⑦ `}` ⑧ `[` ⑨ `]` ⑩ `;` ⑪ `:` ⑫ `::` ⑬ `,` ⑭ `.` ⑮ `->` ⑯ `*` ⑰ `&` ⑱ `=` ⑲ `==` ⑳ `!` ㉑ `!=` ㉒ `+` ㉓ `-` ㉔ `++` ㉕ `--` ㉖ `/` ㉗ `%` ㉘ `+=` ㉙ `-=` ㉚ `*=` ㉛ `/=` ㉜ `%=` ㉝ `&&` ㉞ `||` ㉟ `?` ㊱ `"` ㊲ `'` ㊳ `\` ㊴ `_` ㊵ `~` ㊶ `^` ㊷ `|` ㊸ `<<` ㊹ `>>` ㊺ `<=` ㊻ `>=` ㊼ `//` ㊽ `/* */` ㊾ `...` ㊿ `<=>`

(2)指针的符号:

​	指针这一部分不要理解成“符号乱搭配”,而要先理解成:指针本质上是一个存地址的变量。围绕指针最常见的符号主要是 `*`、`&`、`->`、`.`、`[]` 这些。

​	第一类,指针里面最核心的符号:

- `*` 在声明变量时表示这个变量是指针,比如“某个变量里面存的是地址”;在使用变量时又表示解引用,也就是“通过地址找到它指向的内容”
- `&` 在普通变量前面一般表示取地址,也就是拿到这个变量在内存里面的位置;在函数参数或者变量声明里面,它也可能表示引用
- `->` 表示通过指针访问对象里面的成员,可以理解成“我手里不是对象本身,而是对象地址,所以通过地址去找对象里面的东西”
- `.` 表示通过对象本身访问成员,它经常和 `->` 对比着看:对象本身用 `.`,对象指针用 `->`
- `nullptr` 表示空指针,意思是这个指针现在没有指向一个有效对象,比老写法里面的 `NULL` 更推荐

​	第二类,和指针关系很近,但是不一定一开始就要深入的符号:

- `[]` 常用于数组下标,而数组和指针在 C++ 里面关系很近,所以看数组代码时经常会接触到指针思想
- `++`、`--` 可以让指针向前或向后移动,在数组、底层内存操作里面可能会看到,但入门阶段不建议乱用
- `+`、`-` 可以和指针搭配做地址偏移,这属于更偏底层的写法,看得懂就行,平时不建议优先使用

​	第三类,现代 C++ 里面更推荐用封装来替代的指针写法:

- `new` 和 `delete` 是手动申请和释放内存,但是现代 C++ 更推荐用智能指针或者容器来管理内存
- 裸指针配合 `*`、`&`、`->` 虽然很基础,但是在复杂工程里容易出现空指针、野指针、内存泄漏等问题
- 如果只是传参,很多时候可以用引用来代替指针
- 如果要表示对象所有权,很多时候可以用 `std::unique_ptr` 或 `std::shared_ptr`
- 如果要管理一组连续数据,很多时候可以用 `std::vector`、`std::array`、`cv::Mat`

​	所以指针这一块我的理解是:先记住 `&` 是拿地址,`*` 是通过地址找内容,`->` 是通过地址访问成员。能用引用、容器、智能指针表达清楚的时候,就不要一上来写一堆裸指针。

(3)剩下符号的用法:

​	除去指针相关的符号之后,剩下的符号我觉得只分成“经常使用”和“不经常使用”还不够细,因为有些符号虽然不常手写,但是看别人代码时一定会遇到;还有一些符号不是不会用,而是实际写工程时更推荐用库、类或者函数封装起来。可以先分成下面几类:

​	第一类,经常使用,必须先熟悉:

- `#` 主要用于预处理,比如引入头文件、宏定义等
- `<`、`>` 在比较大小、模板、头文件包含里面都会遇到
- `(`、`)` 用于函数调用、条件判断、控制优先级
- `{`、`}` 用于表示代码块,比如函数、if、for、while、class 的范围
- `[`、`]` 常用于数组下标、vector 下标访问
- `;` 表示一条语句结束
- `,` 用于分隔参数、变量、列表
- `.` 用于对象访问成员
- `=` 用于赋值
- `==`、`!=`、`<=`、`>=` 用于判断条件
- `+`、`-`、`*`、`/`、`%` 用于基本数学运算
- `+=`、`-=`、`*=`、`/=`、`%=` 用于在原变量基础上更新数值
- `&&`、`||`、`!` 用于逻辑判断
- `"` 用于字符串
- `'` 用于字符
- `//` 用于单行注释
- `/* */` 用于多行注释

​	第二类,不一定天天写,但是看代码必须认识:

- `::` 是作用域符号,常见于 `std::`、类的成员函数实现、命名空间
- `:` 常见于三目运算符、构造函数初始化列表、继承、访问权限标签后面
- `?` 一般和 `:` 组成三目运算符,用于简单条件表达式
- `++`、`--` 表示自增和自减,循环里面比较常见
- `\` 常用于转义字符,比如换行、双引号、路径里的特殊字符
- `_` 本身不是运算符,但是常用于变量名、函数名、文件名
- `<<`、`>>` 常用于输入输出,也可以用于位移运算
- `...` 常见于可变参数、模板参数包,入门阶段不需要优先掌握
- `<=>` 是 C++20 里面的三路比较运算符,目前入门和普通视觉工程里不常用

​	第三类,更偏底层或者进阶,实际工程里要谨慎使用:

- `~` 是按位取反,也可以出现在析构函数名字前面
- `^` 是按位异或
- `|` 是按位或
- `&` 除了取地址和引用,也可以表示按位与
- `<<`、`>>` 除了输入输出,也可以表示左移和右移

​	这些位运算符不是不能用,而是它们更偏底层。比如写寄存器、通信协议、图像二值掩码、状态标志位时会用到;但普通业务逻辑、视觉流程、ROS2 节点里面不一定经常手写。

​	第四类,实际写工程时更推荐用封装好的库或者类来替代直接操作:

- 原始数组的 `[]` 很多时候可以用 `std::vector`、`std::array`、OpenCV 的 `cv::Mat` 来管理
- 裸指针相关的 `*`、`&`、`->` 很多时候可以用引用、智能指针、对象封装来减少手动管理
- `new`、`delete` 这类手动内存管理,现代 C++ 里更推荐用 `std::unique_ptr`、`std::shared_ptr`、`std::vector` 等 RAII 封装
- 位运算 `&`、`|`、`^`、`~` 如果只是表达状态,可以考虑用 `enum class`、结构体、类函数来封装含义
- 字符串里的转义符 `\` 如果写复杂路径或者文本,可以考虑用 `std::string`、配置文件、路径库来减少手写错误

​	所以我的理解是:高频符号先熟练,低频符号先能看懂,底层符号不要乱用,能用库和类表达清楚的时候就不要硬写一堆符号。C++ 和 Python 一样,真正写工程时也会大量依赖封装好的库,只是 C++ 更容易暴露底层细节,所以这些符号还是要认识。
